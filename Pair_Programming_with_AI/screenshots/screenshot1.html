Scope & Closure Audit Report

1. Lexical Scope and Captured Variables (Closures)

The function notify() is declared directly inside the execution context of addTask(taskFn, priority). Because JavaScript uses lexical scoping, notify retains access to all variables in its parent function's scope even after outer statements execute.

  • Closed-over variables: notify forms a closure over priority and taskFn from the parameter list of addTask.
  • It also retains reference to the enclosing scope chain up to the module/global object.

2. The Severe Scope Trap: Unbound name

Bug Identified: console.warn(`High priority task added to ${name}.`);

In TaskQueue, name was only a parameter in the constructor(name). It is NOT a parameter of addTask, nor is it a local variable in scope.

  • Node.js: Throws an uncaught ReferenceError: name is not defined as soon as priority > 9 is enqueued, crashing runtime execution.
  • Browser: Falls back to window.name (an empty string or browser window title), producing silent bugs rather than using this.queueName.

3. Block Scoping (let / const) vs Function Scoping

Using let and const enforces block-level boundary constraints (preventing variable leaking and hoisting surprises common with var). In this class, state objects such as taskItem and iteration counters must be scoped strictly to the block where they are defined to prevent accidental state mutation across async cycles.

4. Closure Creation Antipattern

Defining notify() inside addTask() allocates a brand new function instance and closure context on every single call to addTask(). This increases memory overhead and introduces unnecessary garbage collection churn. Logging and alerts belong in dedicated class methods or an external notifier.
